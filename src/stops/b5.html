Counting choices: how big is the search?

Big idea

Backtracking walks a tree of choices: each level is one decision, each branch one option. Before writing one, count that tree. Its depth and branching tell you how many answers there are, how long brute force takes, and how much pruning has to save.

The multiplication principle

If you make one choice with a options and then an independent choice with b options, there are a × b combined outcomes. A 4-digit PIN: 10 × 10 × 10 × 10 = 10⁴. Every count below is this rule applied level by level down the tree.

Combinations divide by k! because each unordered group of k items can be listed in k! orders, and we only want one of them. Picking in increasing index order is how the code makes sure of that.

Count nodes, not just answers

The work is the number of nodes the search visits, not just the leaves. The subset tree has 1 + 2 + 4 + … + 2ⁿ = 2ⁿ⁺¹ − 1 nodes (the sum from stop 0), about twice its leaves. The permutation tree has about e · n! ≈ 2.72 · n! nodes. If recording each answer copies a list of length n, the totals become O(n · 2ⁿ) and O(n · n!).

These limits explain why stop 6 cares so much about pruning. N-Queens with one queen per row has 8⁸ ≈ 16.8 million placements for N = 8; refusing to reuse a column cuts that to 8! = 40,320; checking diagonals too leaves only 92 solutions, and far fewer nodes are ever visited.

Snapshots versus the live list

Backtracking code builds one list cur, adds a choice, recurses, and removes it again. That single list is shared by the whole search (bridge 3.5). When you record an answer, record a snapshot: res.append(cur[:]). Appending cur itself stores a tag to the live list, which the undo steps later empty.

Exam trap

2ⁿ and n! look similar for small n and are wildly different later: at n = 20, 2ⁿ ≈ 10⁶ but n! ≈ 2.4 × 10¹⁸. Say which one your algorithm is, and why (in/out per item, or "any unused item next").

Remember
  • Strings kⁿ, subsets 2ⁿ, permutations n!, ordered picks n!/(n−k)!, combinations C(n, k).
  • Work = nodes visited × work per node, not just the number of answers.
  • Brute force limits: 2ⁿ to n ≈ 25, n! to n ≈ 11.
  • Record cur[:], never cur.
