Two exchange arguments, written out

A greedy answer is only trustworthy with a reason. The reason is an exchange argument: take any optimal solution, show you can swap in the greedy choice without making it worse, then repeat on what is left.

Interval scheduling (most non-overlapping intervals). Greedy: sort by end time, take an interval if it starts at or after the last one taken ended. Why: let G be the interval that ends first overall, and O any optimal schedule. Replace O’s first interval with G. G ends no later than O’s first one did, so it overlaps nothing in the rest of O, and the schedule is still valid with the same size. So some optimal schedule starts with G; remove G and everything it overlaps, and repeat. Sorting by start time or by length has no such argument, and counterexamples are easy to build. LC 435 is “total minus the largest non-overlapping set”; LC 452 (arrows) is the same sweep over right ends:

{{code:min_arrows}}

Fractional knapsack (items may be split). Greedy: take items by value per kilo, best first, splitting the last one. Why: suppose an optimal load holds some of a lower-ratio item B while part of a higher-ratio item A is left behind. Swap a little weight of B for the same weight of A: the value goes up or stays equal. So an optimal load never leaves a better item behind for a worse one.

Memo → table → one row: three full conversions

Your end-sem question may hand you a memoised solution and ask for the table, or the table and ask for one row. The conversion is mechanical. Four steps:

  1. Recursion. Define f(i, j) in words (“the LCS of a[i:] and b[j:]”) and write it with base cases.
  2. Memo. Cache f. Same cells, same answers; only the repeated work disappears.
  3. Table. Allocate every (i, j). Read the arrows: if a cell needs (i + 1, j), (i, j + 1) and (i + 1, j + 1), those must be filled first, so loop backwards. If it needs (i − 1, j) and (i, j − 1), loop forwards. Base cases become the border row and column.
  4. One row. If row i only reads row i + 1 (or i − 1), keep a single list. The cell diagonal to you gets overwritten before you need it, so save it in a variable first.

You already know trees, heaps, DP, graphs and union-find. Contest problems rarely use one tool alone. This stop shows six combinations that appear again and again: DP on a tree, DP on a DAG, binary search plus a check, union-find for more than MST, heaps with greedy, and the trie. None is a new idea; each is two familiar ideas snapped together. It goes slightly beyond the written outline, and every function below was tested.

1. DP on a tree

A tree’s subproblems are its subtrees, and the order is “children before parent”. Compute a small answer for every node from its children’s answers. The simplest safe way to get that order is a stack that lists nodes parent-first, then reversed: every child then comes before its parent, with no recursion, so a 10⁵-long chain cannot crash Python.

  • LC 337 House Robber III. Two numbers per node: best if you rob it, best if you skip it.
  • LC 543 Diameter. A path bends at one node; its length is the left height plus the right height.
  • LC 124 Maximum Path Sum. Going up a path may use only one branch; a path that bends here may use both. Ignore negative branches.

2. DP on a DAG

Any DAG (see stop 12) is a “tree with sharing”: fill the table in topological order. Shortest path, longest path, number of paths, and LC 329 and LC 1857 are all this. The recipe never changes: define the value at a vertex from its predecessors, process vertices in topological order, and a cycle means no answer.

3. Binary search on the answer, with a graph check

If “can we do it with limit x?” is easy to check, and the answer to that question changes from no to yes exactly once as x grows, binary search x. Typical checks are a BFS (LC 1631, 778), a greedy scan (LC 875 Koko, LC 1011 ship packages, LC 410 split array) or a union-find over the edges at most x. The check in LC 1631 appears in stop 12 beside the Dijkstra version; solving a problem two ways and comparing is the best way to catch a mistake. The generic pattern is first_true in stop 14.

Union-find also answers “which items end up in one group?” LC 721 Accounts Merge: two accounts sharing an email are the same person, so union all emails of an account. A trie is a tree with one child per letter; a word is a path ending in a marker. Insert, search and prefix queries cost O(length of the word), independent of how many words are stored. Exam traps

Tree DP with recursion fails on deep trees in Python. In the running median, rebalance after every insert. A trie’s starts_with on an empty prefix is always true; LeetCode prefixes are never empty. The check function in a binary search must be monotone, or the search returns nonsense. A weighted union-find must compress paths and fix the ratios while doing it.

Remember

Tree DP: children first (reverse of parent-first), two numbers per node when a choice depends on the parent. DAG DP: topological order. Binary search: “is x enough?” must flip once. DSU: merge things that must be together; weighted DSU stores ratios or parities. Two heaps: smaller half in a max-heap, larger half in a min-heap. Trie: path = word.

A model answer: “Explain Dijkstra”

“Dijkstra finds shortest paths from one source when no edge is negative. I keep a min-heap of (distance, vertex). I pop the smallest; if it is stale I skip it; otherwise its distance is final, because any other route must go through a vertex still in the heap whose distance is at least as large, and edges cannot make it smaller. I then relax its edges and push improvements. Each edge causes at most one push, so the cost is O((V + E) log V). I would test an unreachable vertex, a graph with one vertex, and two equal-length paths. With a negative edge the finality claim breaks, so I would use Bellman–Ford.”

1. Merge sort

Quick Sort (stop 3) partitions then recurses. Merge sort recurses then merges: split the list in half, sort each half, merge the two sorted halves by repeatedly taking the smaller front item. Every level of the recursion does O(n) merging and there are log₂ n levels, so the cost is O(n log n) in every case, with no bad input. The price is O(n) extra space for the merge.

It is stable: items that compare equal keep their original order, as long as ties are resolved in favour of the left half (<=, not <). Python’s built-in sort is stable too, which is why sorting by one key and then another works.

{{code:merge_sort_stable}}

Hand trace of the merge of [2, 5, 9] and [3, 4, 10]: compare 2 and 3, take 2; 5 and 3, take 3; 5 and 4, take 4; 5 and 10, take 5; 9 and 10, take 9; the left side is empty, so append the rest: [2, 3, 4, 5, 9, 10].

The contest payoff: counting while you merge

An inversion is a pair i < j with a[i] > a[j]. During a merge, when you take an item from the right half while left items remain, that right item is smaller than all of them: you have just counted that many inversions in O(1). This turns the O(n²) pair count into O(n log n). The same idea answers LC 315 (for each element, how many later elements are smaller; sort the indices so you remember who is who) and LC 493 (count pairs with a[i] > 2·a[j] in a separate sweep before each merge, since both halves are sorted). Stop 2 uses merge sort to show the recurrence T(n) = 2T(n/2) + O(n), and the sorting patterns in stop 3 have a plain count_inversions; LC 912 itself is simply “implement a sort”.

2. Amortised analysis

Some operations are usually cheap and occasionally expensive. Amortised cost is the average per operation over a whole sequence, worst case guaranteed. It is not average over random inputs.

The dynamic array. list.append is O(1) most of the time, but when the array is full it allocates a bigger one and copies everything. If the capacity doubles, the copies happen at sizes 1, 2, 4, 8, …, and the sum of that series is less than 2n. So n appends cost under 3n elementary steps in total: O(1) amortised per append. If the capacity grew by only 1 each time, the copies would be 1 + 2 + … + (n − 1) = n(n − 1)/2, which is O(n²). The multiplicative growth is what matters.

The code counts the copies: after n appends with doubling, copies < 2n; with growth by one it is exactly n(n − 1)/2 (both asserted for sizes up to 5,000).

Other costs you have been quoting. Building a heap from n items is O(n), not O(n log n), because most nodes are near the bottom and sift down only a step or two (stop 5). Union-find with union by size and path compression costs O(α(n)) amortised per operation, where α is the inverse Ackermann function, below 5 for any input that fits in a computer; that is why Kruskal’s sort dominates its running time. Monotonic stacks are O(n) because each element is pushed once and popped at most once, however many pops one step makes. All three use the same accounting idea: a charge per item, paid once.

3. Hashing, and what a dict does

A hash table stores a key at position hash(key) % size. Two keys can land on the same position: a collision. There are two standard answers.

  • Chaining. Each position holds a small list of the entries that landed there. Lookup walks one list. Simple, and deletes are easy.
  • Open addressing. One entry per slot; on a collision, probe the next slot (linear probing: the next one, then the next…). A deleted slot must become a tombstone, not empty: an empty slot ends a search, and would cut off the keys that were placed after it.

The load factor is entries ÷ slots. As it rises, chains lengthen and probe runs grow, so tables resize (usually doubling) and re-place every key, which is another amortised O(1) argument. With a good hash and a controlled load factor, insert, lookup and delete cost O(1) on average. The worst case is O(n), if every key collides. This is why Python’s dict and set are fast but can be slowed by an adversarial input in a contest, and why keys must be hashable (a list is not; use a tuple).
