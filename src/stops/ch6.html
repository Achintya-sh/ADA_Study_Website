Backtracking line

Backtracking

Big idea

Complete search done politely: build an answer one choice at a time, and the moment a choice cannot work, take it back.

Two ideas to start from

Recursion (chapter 1): a function that solves a smaller version of itself. Complete search: when no clever shortcut exists, try every possibility. A 4-dial lock with digits 0–9 has 10⁴ = 10,000 combinations; try them all.

Complete search has two problems: (1) how do you write the loops when the number of dials depends on the input? (2) how do you avoid wasting time on obviously bad combinations? Backtracking answers both: (1) with recursion, (2) with pruning.

Backtracking, defined

Remember

Backtracking is an organised complete search. You build the solution step by step, one decision at a time. If a decision leads to a dead end, undo it and try the next option.

At every step, the same three moves:

  1. Choose: add one option to the current partial solution.
  2. Explore: recurse to make the next decision.
  3. Undo: remove that option so the state is exactly as it was, then try the next option.

Analogy: a rat in a maze walks down a corridor. If it hits a wall it walks back to the last junction and tries a different corridor. Doctor Strange viewing 14,000,605 futures does the same: follow a decision, see whether it wins, rewind if it does not.

Teacher's note

Picture the search as a tree. The root is "no decisions yet". Each edge is a decision. Each node is a partial solution. A leaf is either a complete answer or a dead end. Going down an edge is choose + explore. Coming back up is undo. The program is simply a depth-first walk of this tree (that is why chapter 8's DFS will feel familiar).

The universal template

Exam trap

The #1 bug: forgetting to undo (or undoing incompletely). If the state after the call is not identical to the state before it, the next iteration starts from a corrupted state. Always ask: "what did I change when I chose? Did I change it back?" Also: when you save a solution, save a copy (curr[:]), not the list itself, or later undos will erase what you saved.

How to design a backtracking solution

Before writing any code, answer five questions. They turn a vague problem into a template you fill in.

  1. What is the state? What do I need to remember about the decisions made so far? (The partial answer, plus any helper data such as visited or a count.)
  2. What is one decision? At each step I fill one position / pick one element / place one queen.
  3. What are the options for that decision? The loop's range: each character, each unused number, each column, include-or-exclude.
  4. When is a choice invalid? The pruning test, checked before recursing.
  5. When am I done, and how do I undo? The base case (answer complete) and the exact reverse of every change made when choosing.

Counting the work. The running time is roughly (number of nodes in the decision tree) × (work per node). With b options per level and depth d, that is up to bᵈ leaves. Pruning cuts whole subtrees but the worst case can stay exponential.

Problem 1: generate every password of length n

Alphabet "aeiou1234@" (10 characters), length n. We need n nested loops, but n is only known at run time. Recursion solves that: each call fills one position. The state is i (the position being filled) and curr (characters chosen so far).

Pruning: cut dead branches early

Now add rules: (1) no two equal characters in a row, (2) at most two digits. The lazy way generates all 10n passwords and filters. The smart way checks before recursing. If the choice already breaks a rule, skip it, and with it the entire subtree below, which might contain 10n−i useless leaves.

Watch the difference on a small case. Choose one of the four problems and step through (the last one, subsets, is the include / exclude pattern). In the tree, red nodes are pruned: they are created, rejected, and their whole subtree is never visited.

Problem 2: permutations (no repeats)

Arrange the numbers 1..n in every possible order. At each position choose a number that is not already used. A boolean visited array answers "already used?" in O(1) (checking num in curr would cost O(n) each time). There are n! results.

Compare with sequences with repetition (no visited array: 1..n each position, nn results). The only difference is the pruning line.

Problem 3: N-Queens

Place N queens on an N × N chessboard so that no two attack each other: no two share a row, a column, or a diagonal.

Teacher's note

The clever framing. A naive search picks N squares out of N² (a huge number). But we already know that each row holds exactly one queen. So just decide, row by row, which column that row's queen goes in. The decisions are now "column for row 0, column for row 1, …": a tree of depth N with N options per level, pruned heavily.

Plan: process row 0, 1, 2, … For the current row try each column. If the square is safe (not attacked by queens already placed above), place a queen and move to the next row. If no column in a row works, return, and the previous row's queen is moved to its next column. That "return and move on" is the backtrack.

Why only check upward? We fill rows from the top. Rows below the current one are still empty, and the current row has no other queen. Only rows 0 .. row−1 can contain attackers.

Added: missing from your notes

Faster safety check in O(1). Two queens share a "\" diagonal exactly when row − col is equal, and a "/" diagonal exactly when row + col is equal. Keep three sets: used columns, used (row−col) values, used (row+col) values. Safe means the column, row−col and row+col are all absent from the sets. Add them when you choose and remove them when you undo.

Step through the N = 4 case and watch each "attacked" skip and each undo. Try N = 5 and N = 6 and use "Next solution".

Backtracking is exponential in the worst case. Pruning does not change the worst-case bound, but it can cut the real running time by orders of magnitude. The art is finding the earliest possible moment to say "this can never work".

Choosing by n

n ≤ 10: all orderings (10! ≈ 3.6 million). n ≤ 20: all subsets (2²⁰ ≈ 10⁶), with pruning. n ≤ 40: meet in the middle (2²⁰ per half). Larger: this is not a backtracking problem; look for DP or a greedy.

Exam traps

Append cur[:], not cur: otherwise every saved result is the same list that later gets emptied. Undo exactly what you did. Skip duplicates with i > start (same depth), not i > 0. Pruning before recursing is cheaper than pruning after.

Remember

Choose, recurse, undo. Sort and skip equal siblings. Big items first, skip identical states.

Precompute the yes/no test (palindrome table), then branch only on yes.

Count or best value with repeating states → DP. n ≤ 40 counting → meet in the middle.
