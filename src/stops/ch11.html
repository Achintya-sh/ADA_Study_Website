Greedy algorithms

Big idea

A greedy algorithm builds the answer one choice at a time, always taking the option that looks best right now, and never goes back. It is usually just "sort, then one pass", so it's fast and short. The catch: it's only correct when you can argue that the locally best choice never ruins the global answer.

Greedy versus DP in one picture

DP (stops 9–10) tries every choice for the last step and keeps the best. Greedy commits to one choice and never reconsiders. When greedy is correct it is simpler and faster; when it isn't, it gives a confident wrong answer. Bridge 8.5's coins show both sides: with coins 1, 5, 10, 25 "biggest coin first" is optimal; with 1, 3, 4 it isn't.

How to know a greedy is right: the exchange argument

CLRS (3rd edition, §16.1–16.2) proves greedy algorithms with one recurring move. Take any optimal solution. If it doesn't start with the greedy choice, swap the greedy choice in and show the solution is still valid and no worse. Then the greedy choice is safe, and the same argument repeats on what's left.

Worked example: activity selection (CLRS §16.1)

Pick as many non-overlapping activities as possible. Greedy rule: always take the activity that finishes earliest among those that start after the last one you took.

Why it works: let A be any optimal schedule and a its first activity. The earliest-finishing activity g ends no later than a, so replacing a with g can't clash with anything later in A. The schedule is still valid and still has the same size. So some optimal schedule starts with g, and the argument repeats on the activities that start after g ends.

Solution: 881 Boats to Save People (1530). Try it first.

The heaviest person has to leave on some boat. Give them the lightest partner if one fits; if even the lightest doesn't fit, nobody does. Exchange argument: swapping any other partner for the lightest never makes things worse.

Solution: 1029 Two City Scheduling (1348). Try it first.

Send everyone to B, then decide who to move to A. Moving person i changes the cost by a − b, so move the n people with the most negative a − b.

Solution: 2208 Minimum Operations to Halve Array Sum (1550). Try it first.

Halving the largest number always removes the most, so do that every time. Python's heapq is a min-heap: store negatives to get a max-heap.

Solution: 1647 Minimum Deletions to Make Character Frequencies Unique (1510). Try it first.

Go through the frequencies from largest to smallest. If a frequency is already taken, lower it until it's free (or reaches 0); each step down is one deletion.

Exam traps

Sorting by the wrong key (start vs end). Getting the tie at a shared endpoint wrong: in 435 intervals [1,2] and [2,3] don't overlap (>=), but in 452 balloons that touch share an arrow (>). Trusting a greedy that passed the examples: try to break it with a small counterexample first; if you can, switch to DP.

Remember
  • Greedy = commit to the locally best choice, never undo. Usually sort + one pass.
  • Prove it with an exchange argument; disprove it with one small counterexample.
  • Most activities / fewest removals: sort by end. Merging: sort by start.
  • Pairing: sort + two pointers. Assigning to A or B: sort by the difference. "Largest each time": a heap.

Two exchange arguments, written out

A greedy answer is only trustworthy with a reason. The reason is an exchange argument: take any optimal solution, show you can swap in the greedy choice without making it worse, then repeat on what is left.

Interval scheduling (most non-overlapping intervals). Greedy: sort by end time, take an interval if it starts at or after the last one taken ended. Why: let G be the interval that ends first overall, and O any optimal schedule. Replace O’s first interval with G. G ends no later than O’s first one did, so it overlaps nothing in the rest of O, and the schedule is still valid with the same size. So some optimal schedule starts with G; remove G and everything it overlaps, and repeat. Sorting by start time or by length has no such argument, and counterexamples are easy to build. LC 435 is “total minus the largest non-overlapping set”; LC 452 (arrows) is the same sweep over right ends:

Fractional knapsack (items may be split). Greedy: take items by value per kilo, best first, splitting the last one. Why: suppose an optimal load holds some of a lower-ratio item B while part of a higher-ratio item A is left behind. Swap a little weight of B for the same weight of A: the value goes up or stays equal. So an optimal load never leaves a better item behind for a worse one.

When the same greedy fails

Both failures below are the same mistake: the choice changes what fits later in a way a single number cannot summarise.

0/1 knapsack (no splitting). Items (value, weight): (60, 10), (100, 20), (120, 30), capacity 50. Ratios 6, 5, 4, so ratio-greedy takes the first two for 160 and strands 20 unused kilos; the best is the last two for 220. The exchange argument breaks because you cannot swap “a little”. Use DP (stop 10).

Coin change. Coins 1, 3, 4 and amount 6: greedy takes 4 + 1 + 1 (three coins), but 3 + 3 uses two. For the coins 1, 5, 10, 25 greedy happens to be optimal, but proving that for a given set is hard, so default to the DP.

Rule of thumb: if you can say “whatever I do, taking this one first is never worse” and defend it with a swap, go greedy. If you cannot, or a small counterexample appears, do DP. Try the counterexample first: it takes thirty seconds.

More greedy problems with tested code

LC 621 Task Scheduler. The busiest task, say A with count top, forces top − 1 gaps of width n + 1 and a final row; every task tied with A’s count adds one slot to the last row. If there are more tasks than that frame needs, no idling is required and the answer is simply the number of tasks.
