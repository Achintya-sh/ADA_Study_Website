Graphs I: concepts and representation

Big idea

Trees were a special case. Graphs describe any set of things and the connections between them. First the vocabulary, then three ways to store a graph in memory.

Where graphs come from: the Königsberg bridges

In 1736 the city of Königsberg had a river with two islands and seven bridges. Residents wondered: can you take a walk that crosses every bridge exactly once? Euler's breakthrough was to throw away everything irrelevant (the shape of the river, the distances) and keep only the connections: four land masses as dots, seven bridges as lines between them. This invented graph theory.

Added: missing from your notes

Euler's rule. A walk using every edge exactly once exists only if the graph is connected and has 0 or 2 vertices of odd degree. Königsberg has four, so the walk is impossible. (This also shows why the sum of degrees is always even: each edge adds 1 to two vertices.)

What is a graph?

Remember

A graph G = (V, E) is a set of vertices (nodes, the objects) and a set of edges (the connections between pairs of vertices). That is all.

Cities and roads. Computers and cables. People and friendships. Web pages and links. Courses and their prerequisites. A chessboard square and the squares a knight can reach.

Remember

Counting rules. Undirected: sum of all degrees = 2E (handshake lemma). Directed: sum of in-degrees = sum of out-degrees = E. Maximum edges with V vertices: undirected V(V−1)/2, directed V(V−1). Since E ≤ V², we have log E = O(log V).

A linked list is a very thin tree, and a tree is a graph with no cycles. So everything you know about tree traversal carries over, with one new danger: cycles. That is why graph traversal needs a visited array.

Vertex names. In code we usually number vertices 0 .. V−1 so we can use arrays. If vertices have names (cities), either map each name to a number with a dictionary, or key the adjacency list by name: adj = {"Delhi": ["Agra", "Jaipur"], "Agra": ["Delhi"], …}.

Three ways to store a graph

1. Edge list

Just a list of the edges. Simplest. Weighted: add the weight as a third element.

Space O(E). To ask "is there an edge u–v?" you must scan the list: O(E). To list the neighbours of u, scan everything: O(E). Good when the algorithm just processes edges in bulk (e.g., sorting edges by weight).

2. Adjacency matrix

A V × V table. Cell [i][j] is 1 if there is an edge from i to j, else 0 (for weighted graphs store the weight). For an undirected graph the matrix is symmetric (matrix[i][j] == matrix[j][i]).

Space O(V²), even if there are few edges. Edge check: O(1). Listing neighbours of u: scan a whole row, O(V). A graph of 100,000 vertices would need 10¹⁰ cells (~10 GB): impossible.

3. Adjacency list (the one you will use most)

For each vertex, store the list of its neighbours.

Space O(V + E). Listing neighbours of u: O(deg(u)), exactly what traversals need. Edge check u–v: O(deg(u)).

Exam trap

The order of neighbours inside an adjacency list changes the order of visits in DFS and BFS (but not correctness). Your notes build the list for the same graph as 0:[3,1,2] (insertion order); sorted order gives 0:[1,2,3]. If an exam gives you the adjacency lists, visit neighbours in the order given.

Added: missing from your notes

Implicit graphs. A grid maze or a board is a graph you never store: each cell is a vertex, and its neighbours are computed on the fly (up, down, left, right). Rotting oranges and counting islands (chapter 8) work this way.
