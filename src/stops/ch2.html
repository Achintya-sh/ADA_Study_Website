Complexity analysis

Big idea

Time and space complexity, Big-O and its relatives, best/average/worst case, and how to solve the recurrences that recursive algorithms produce.

Why we count operations, not seconds

The same program runs at different speeds on a laptop and on a phone, in Python and in C. Seconds therefore tell us about the machine. What we want is a property of the algorithm: how does the number of basic operations grow as the input grows?

Teacher's note

Think of two taxi companies. One charges a flat fee however far you go. The other charges per kilometre. For a 1 km trip the flat fee looks bad. For a 100 km trip it wins easily. Complexity analysis is about the 100 km trip: what happens for large n. That is why we ignore small inputs and constant details.

Two rules for simplifying

  1. Drop constant factors. 5n² and n² grow the same way: double n and either one becomes 4× bigger.
  2. Drop smaller terms. In n³ + n² + n, once n is large the n³ part is almost everything.

Applying both rules to a running time gives its order of growth, written with Big-O.

Exam trap

The triangular loop (for j in range(i)) trips up many students. It is not n log n and it is not "half of n". It sums to n(n−1)/2, which is n²/2 − n/2, and dropping constants and the lower term leaves O(n²).

A recipe for analysing any code

  1. Decide what n is. The size of the input: array length, number of nodes, number of vertices. If there are two inputs (arrays of lengths n and m), keep two variables: a nested loop over both is O(n·m), not O(n²).
  2. Find the basic operation: the line that runs the most (usually the innermost statement or a comparison).
  3. Count how many times it runs as a function of n. Work from the inside out: a loop's count is (iterations) × (cost of its body).
  4. Combine: statements in sequence add; nesting multiplies; an if/else costs the larger branch (for worst case).
  5. Simplify: drop constants and lower-order terms.

The standard ladder of growth rates

From fastest to slowest: O(1) constant, O(log n) logarithmic, O(n) linear, O(n log n) linearithmic, O(n²) quadratic, O(n³) cubic, O(2ⁿ) exponential, O(n!) factorial. CLRS adds a formal fact: any exponential with base above 1 eventually beats any polynomial (nᵇ = o(aⁿ)), and n! grows faster than 2ⁿ.

Asymptotic notation, formally

Your lecture notes use Big-O loosely. CLRS gives five precise symbols. Each describes a set of functions, and "f(n) = O(g(n))" really means "f(n) belongs to that set".

SymbolPlain meaningFormal definitionLike…
O(g)Upper bound: f grows no faster than g∃ c > 0, n₀ such that 0 ≤ f(n) ≤ c·g(n) for all n ≥ n₀≤
Ω(g)Lower bound: f grows at least as fast as g∃ c > 0, n₀ such that 0 ≤ c·g(n) ≤ f(n) for all n ≥ n₀≥
Θ(g)Tight bound: both of the above∃ c₁, c₂ > 0, n₀ such that c₁·g(n) ≤ f(n) ≤ c₂·g(n) for all n ≥ n₀=

Remember

Key theorem: f(n) = Θ(g(n)) if and only if f(n) = O(g(n)) and f(n) = Ω(g(n)).

Proving it with constants: 3n² + 10n + 5 = O(n²)

We must find c and n₀. Try c = 4. We need 3n² + 10n + 5 ≤ 4n², which rearranges to n² − 10n − 5 ≥ 0. At n = 10 this gives −5 (fails). At n = 11 it gives 6 (works), and it keeps working after that. So c = 4, n₀ = 11 is a valid witness. The lab below lets you hunt for constants yourself.

Exam trap

Big-O is not "worst case". These are two different axes. Which input? (best, average, worst case) is one question. Which bound on the resulting function? (O, Ω, Θ) is another. You can say "the worst-case time of Quick Sort is Θ(n²)" and "the best-case time is Θ(n log n)". Your lecture notes use "Big-O" and "worst case" together as shorthand: "O(n²) means for every input, the time is at most c·n²".

Best, average and worst case

The running time often depends on which input of size n you are given, not just n.

  • Best case: the input that makes the algorithm fastest.
  • Worst case: the input that makes it slowest. This is the usual default, because it is a guarantee.
  • Average case: the expected time over all inputs (needs an assumption about how inputs are distributed).

Space complexity

Space complexity counts the extra memory an algorithm needs as n grows. Usually we count auxiliary space: memory beyond the input itself.

  • A few variables: O(1). An in-place swap, a running total.
  • A new array or set of size n: O(n).
  • Recursion: the call stack counts. Depth d means O(d) space. Merge sort needs O(n) for merging; Quick Sort needs O(log n) on average for the stack.

Divide and conquer and recurrences

Divide and conquer has three steps: divide into smaller subproblems of the same kind, conquer by solving them recursively, combine the answers. Merge sort: split the array in half, sort each half, merge. The time is described by a recurrence relation, a one-line equation for a recursive function:

Remember

T(n) = a·T(n/b) + f(n)

a = number of subproblems per call. b = how much the input shrinks. f(n) = work done outside the recursive calls (dividing and combining).

Merge sort: a = 2, b = 2, f(n) = n (merging), so T(n) = 2T(n/2) + n.

Method 1: the recursion tree

Draw every call as a node, write the work at each node, add up each level, then add up the levels. For T(n) = a·T(n/b) + f(n):

LevelNodesWork per nodeWork in the whole level

last: logbnalog_b n = nlog_b af(1) = constantnlog_b a

The tree has about logbn levels. The total depends on how the level sums change as you go down, and there are only three patterns:

Growing

1 + 2 + 4 + … + n. The last term dominates. Total ≈ the last level.

Equal

n + n + … + n over log n levels. Total = one level × number of levels = n log n.

Shrinking

n² + n²/2 + n²/4 + …. The first term dominates. Total ≈ the root.

Worked example

T(n) = 3T(n/4) + cn² (CLRS). Level i has 3i nodes, each costing c(n/4i)², so the level costs (3/16)i·cn². Ratio 3/16 < 1, so the sum shrinks like a geometric series: total ≤ cn²·(1 / (1 − 3/16)) = (16/13)cn². Root dominates, T(n) = Θ(n²).

Unbalanced split T(n) = T(n/3) + T(2n/3) + cn. Every level costs at most cn. The longest path shrinks by 2/3 each step, so its length is log3/2n. Total = O(n log n). This is why Quick Sort stays fast even with uneven splits.

Method 2: the Master theorem (the cookbook)

For T(n) = a·T(n/b) + f(n) with a ≥ 1, b > 1, compute the watershed function nc where c = logba (this is the number of leaves). Then compare f(n) with nc. Whoever is bigger "wins".

3. Root heavyf(n) is polynomially larger: f(n) = Ω(nc+ε), and a·f(n/b) ≤ k·f(n) for some k < 1 (regularity)Top level dominatesT(n) = Θ(f(n))
Added: missing from your notes

Two details your slide notes skip. (1) "Smaller" and "larger" must be polynomially so, by a factor of nε for some ε > 0. (2) Case 3 needs the regularity condition. Polynomials like n² always satisfy it. The famous gap: T(n) = 2T(n/2) + n log n. Here c = 1 and f(n) = n log n is larger than n, but only by a log n factor, which is smaller than nε for every ε > 0. The theorem does not apply. Use a recursion tree: log n levels each costing about n log n, so the answer is Θ(n log² n).

Method 3: substitution (guess and prove)

Guess the answer, then prove it by induction. Example: T(n) = 2T(⌊n/2⌋) + n, guess T(n) ≤ c·n lg n. Assume it holds for smaller values:

T(n) ≤ 2·c⌊n/2⌋·lg⌊n/2⌋ + n ≤ c·n·lg(n/2) + n = c·n·lg n − c·n + n ≤ c·n·lg n, as long as c ≥ 1.

Added: missing from your notes

Trick when the induction almost works. If proving T(n) ≤ cn + d fails, strengthen the guess by subtracting a lower-order term: try T(n) ≤ cn − d. A stronger hypothesis gives you more to work with in the inductive step.

Amortised analysis, in one paragraph

Added: missing from your notes

A Python list.append is "O(1) amortised". Occasionally the array is full and must be copied to double its size, costing O(n). But that expensive copy happens only after n cheap appends, so spread over all appends the average cost per append is O(1). Amortised means average over a sequence of operations, with no randomness involved. It also explains why building a heap with n inserts costs O(n log n) but the cleverer build-heap costs O(n).
