Contest toolkit

Big idea

Contests reward the same small set of habits: read the limits first, write a brute force, trust nothing you haven’t stress-tested, and know your standard library so no minute is lost to typing. This stop collects them, plus the Python tools and tricks that sit just outside the lecture notes but pay off on every topic.

Ratings: Codeforces and LeetCode, side by side

The Ladder shows both. CF ratings come from Codeforces contests (a problem rated 1600 is solved by about half of the contestants rated 1600). LC ratings are the community estimates for LeetCode contest problems; classics that never appeared in a contest have none. The two scales aren’t officially linked and LeetCode’s run higher. Python manages about 10⁷ simple operations per second, so the useful budget is smaller than in C++: an O(n²) with n = 5,000 (2.5·10⁷) is borderline, and 10⁵ squared is hopeless.

The routine for every problem

  1. Read the constraints and the subtasks before the story. Write down what each limit allows.
  2. Work one example by hand and restate the problem in one line using graph, DP or sorting words.
  3. Write the most obvious correct solution (simulate, try everything). Aim for about 10 minutes.
  4. Submit it. Marks are in the bank before you start thinking hard.
  5. Use it as a microscope: print its answers for tiny inputs and look for what repeats or stays fixed.
  6. Write the fast version, stress-test it against the brute force, then submit.

On the unseen hard problems of the end-sem, steps 3 and 4 are worth more than any single clever idea: Chakravyuh’s first subtask needed only an eight-line brute force.

Python for contests

Input and output. Calling input() hundreds of thousands of times is slow on its own; read everything once and print once. Unseen Codeforces problems use standard input and usually several test cases:

“The sum of n over all test cases is at most 2·10⁵” means you size arrays per test, never at the maximum for every test.

Speed. Local variables are faster than globals, so put the work inside a function. List comprehensions beat explicit loops. Lists of lists beat defaultdict(list) when keys are 0 to n − 1. Appending to a string with += in a loop is fine in CPython, but join a list when in doubt. Some judges run PyPy, which is much faster on plain loops but slower at some built-ins: use whichever interpreter the judge uses and test with it.

Hash-map attacks. On Codeforces some tests are built to make Python’s dict and set collide and slow to a crawl. If a hash-heavy solution times out for no visible reason, sort instead (bisect on a sorted list) or XOR the keys with a random 32-bit number before inserting.

Deep recursion. The default limit is about 1,000 calls. Prefer an explicit stack or queue for graphs and write DP bottom-up. When you must recurse deeply, raise the limit and run in a thread with a big stack:

Floats. Compare with a tolerance, or avoid floats: ratios as fractions of integers, square roots with isqrt.

Array tricks that appear everywhere

Binary search on the answer. “Minimise the maximum”, “smallest x such that …”: if “can it be done with value x?” goes False, False, …, True, True as x grows, search for the first True. You only write the yes/no check, often a greedy or a BFS.

Prefix sums, difference arrays and a sliding window. Prefix sums turn “sum of a range” into a subtraction, and with a dictionary they count subarrays with a given sum even with negatives. A difference array applies many range additions in O(n + ops). A window whose left end never moves back finds the shortest subarray with a large enough sum in O(n).

Fenwick tree. Prefix sums with point updates in O(log n): the first step beyond the course when a problem mixes “change one value” with “sum of a range”.
